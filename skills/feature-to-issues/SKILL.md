# /feature-to-issues — Issue Manifest Generator

**Inputs:**
- `docs/features/feature-summary.md` ✓
- `docs/features/F-XX-*.md` ✓ (one per feature)
- `ai-context/ui-design.md` ✓ (if present — from /design-ui; provides SCR-NNN/CMP-NNN IDs and mockup paths for UI issues)
- `ai-context/test-plan.md` ✓ (if present — from /write-test-plan; provides UT-/IT-/SMK-/RT- IDs per feature)

**Output:** `ai-context/issues.json`

Run immediately. No preamble.

---

## Step 1 — Read Features

Read `docs/features/feature-summary.md` for the full feature list, wave order, and
dependency graph.

Then read each `docs/features/F-XX-[slug].md` for:
- Purpose, User Stories, Acceptance Criteria
- Functional Requirements covered
- Roles Involved
- Execution Wave
- Dependencies (Depends on / Blocks)

## Step 1.5 — Load UI Design (Screen References)

**Primary source — `## Screen References` sections in each `F-XX-*.md` feature file:**

When reading each `docs/features/F-XX-[slug].md` in Step 1, look for a `## Screen References`
section at the end of the file (written by /design-ui):

```markdown
## Screen References
*(Generated by /design-ui — do not edit manually)*

| Screen ID | Screen Name | Mockup Path |
|-----------|-------------|-------------|
| SCR-NNN   | [Name]      | docs/design/mockups/SCR-NNN-[slug].html |
```

If the section exists, extract the SCR-NNN IDs and mockup paths for that feature and use them
as the authoritative source for UI issue bodies. Build a lookup:

```
feature_id → [{ screen_id, screen_name, mockup_path }]
```

**Fallback source — `ai-context/ui-design.md`:**

If a feature file has no `## Screen References` section but `ai-context/ui-design.md` exists,
read that file and build the same lookup from its Screen Inventory table. Note which features
used the fallback source — report them in the HIL summary.

**Halt condition — both sources absent for a UI feature:**

If `has_frontend` is true AND a feature has no `## Screen References` in its F-XX-*.md AND
`ai-context/ui-design.md` is also absent or doesn't list screens for this feature, halt:

```
⛔ UI DESIGN MISSING FOR FEATURE F-XX

Feature F-XX has no Screen References in its feature file and no entry in
ai-context/ui-design.md.

UI issues cannot be generated without approved screen designs.

Required action:
  1. Run /design-ui to generate mockups and wire SCR-NNN IDs into feature files
  2. Then re-run /feature-to-issues

Do NOT create a UI issue for F-XX without SCR-NNN references.
```

This lookup is used in Step 2: every UI-layer issue body gets a **UI Design Reference**
section citing the exact SCR-NNN IDs and mockup paths.

## Step 1.6 — Load Test Plan (if present)

If `ai-context/test-plan.md` exists (generated by /write-test-plan), read it and build a lookup:

```
feature_id → { ut_ids: [], it_ids: [], smk_ids: [], rt_ids: [] }
screen_id  → { ut_ids: [] }   (the 6 screen-level unit test IDs)
```

This lookup is used in Step 2: every issue body gets a **Test IDs** section listing
the owned UT-/IT-/SMK-/RT- IDs that Ralph-impl or Ralph-test must write and pass.
If `ai-context/test-plan.md` is absent, skip this step silently and omit the section.

---

## Step 1.7 — Load Frontend Declaration

Read `ai-context/ralph-agent-spec.md` (if it exists) and extract:
- `has_frontend` — true / false
- `frontend_stack` — e.g. "React 18 + Vite + MUI v5"

If the file is absent or has no `has_frontend` field, default to:
- `has_frontend = true` if `ai-context/ui-design.md` exists
- `has_frontend = false` otherwise

---

## Step 2 — Derive Issues from Features (LAYER-SPLIT — one issue per layer per feature)

⚠️ **MANDATORY**: For each feature, generate **one issue per implementation layer**, not one issue
per user story. Every feature MUST have ALL of the following layers represented as separate issues:
`DB`, `API`, `UI` (if has_frontend is true), `INT`, `TEST`, `E2E`.

Generating story-based monolithic issues (one issue covering DB+API+UI together) is **wrong** and
will cause /ralph to skip UI implementation entirely. Always split by layer.

**Issue ID format:** `F[XX]-[LAYER]-[NNN]` where NNN is zero-padded per feature.
Examples: `F01-DB-001`, `F01-API-001`, `F01-UI-001`, `F01-INT-001`, `F01-TEST-001`, `F01-E2E-001`

**Issue title format:** `[F-XX] [Feature Name] — [LAYER] Layer`
Examples:
- `[F-01] User Authentication — DB Layer`
- `[F-01] User Authentication — API Layer`
- `[F-01] User Authentication — UI Layer`
- `[F-01] User Authentication — Integration Layer`
- `[F-01] User Authentication — Integration Tests`
- `[F-01] User Authentication — E2E Tests`

**Layer dependency order (within a feature):** DB → API → UI → INT → TEST → E2E
Each layer is blocking the next (except UI which is parallel to API and also blocked by DB).

### DB Layer Issue Body

```markdown
## Feature
F-XX — [Feature Name]

## Layer
DB — Database schema, migrations, and seed data

## Description
[Purpose paragraph from the feature file]

## Acceptance Criteria (DB)
- [ ] Migration files created and reversible (up + down)
- [ ] All tables follow snake_case plural naming
- [ ] All FKs enforced at DB level
- [ ] Seed data created if required
- [ ] Soft-delete pattern applied (deleted_at column where applicable)

## Functional Requirements Covered
| FR-ID | Requirement | Priority |
|-------|-------------|----------|

## Scope
Write migration files and seed files ONLY. No application code.

## Test IDs (DB)
*(Included when ai-context/test-plan.md exists)*
| Type | IDs | Who writes them |
|------|-----|-----------------|
| Unit (UT-) | [DB-specific UT- IDs] | Ralph-impl — same PR |

## Dependencies
Blocked by: [list of prior-feature DB issues, or NONE]

## Definition of Done
- [ ] Migration files exist and are reversible
- [ ] `dotnet ef migrations` (or equivalent) runs without error
- [ ] Seed data idempotent and correct
- [ ] All owned UT- IDs written and passing
- [ ] PR merged and issue closed
```

### API Layer Issue Body

```markdown
## Feature
F-XX — [Feature Name]

## Layer
API — Controllers, services, DTOs, and business logic

## Description
[Purpose paragraph from the feature file]

## User Stories
[List all user stories from the feature file]

## Acceptance Criteria (API)
- [ ] AC-n: [condition from feature file]

## Functional Requirements Covered
| FR-ID | Requirement | Priority |
|-------|-------------|----------|

## Scope
Implement: controllers, service layer, DTOs, validators, repositories (no UI code).

## API Contract (REQUIRED)
Every response MUST be wrapped in ApiResponse<T>:
```json
{ "data": T }
```
NEVER return bare arrays or `{ "items": [...] }` or `{ "result": [...] }`.

Endpoints to implement:
| Method | Path | Request Body | Response ApiResponse<T> |
|--------|------|-------------|------------------------|
| [METHOD] | /api/[resource] | [DTO] | ApiResponse<[T]> |

## Test IDs (API)
*(Included when ai-context/test-plan.md exists)*
| Type | IDs | Who writes them |
|------|-----|-----------------|
| Unit (UT-) | [API-specific UT- IDs] | Ralph-impl — same PR |

## Dependencies
Blocked by: F-XX-DB-001 (DB layer must be complete first)

## Definition of Done
- [ ] All endpoints return `{ "data": T }` — no bare arrays
- [ ] TypeScript / C# types imported from shared contract file — never redefined locally
- [ ] All owned UT- IDs written, assert `response.body.data` exists
- [ ] `tsc --noEmit` or equivalent compile check passes with zero errors
- [ ] PR merged and issue closed
```

### UI Layer Issue Body

*(Only generated when has_frontend is true. If has_frontend is false, skip this layer entirely.)*

```markdown
## Feature
F-XX — [Feature Name]

## Layer
UI — React components, pages, Redux state, and API client integration

## Description
[Purpose paragraph from the feature file]

## User Stories
[List all user stories from the feature file]

## Acceptance Criteria (UI)
- [ ] AC-n: [condition from feature file — UI/UX perspective]

## Functional Requirements Covered
| FR-ID | Requirement | Priority |
|-------|-------------|----------|

## UI Design Reference
*(Mandatory — sourced from `## Screen References` in F-XX-*.md, fallback: ai-context/ui-design.md)*
| Screen ID | Screen Name | Mockup Path |
|-----------|-------------|-------------|
| SCR-NNN   | [Name]      | [docs/design/mockups/SCR-NNN-slug.html](../docs/design/mockups/SCR-NNN-slug.html) |

Ralph-impl MUST implement ALL screens listed above to match the approved mockup exactly.
Navigation links and Primary Actions from the mockup must be wired in the real implementation.
If no SCR-NNN is available (neither feature file nor ui-design.md has screens for this feature),
this issue MUST NOT be created — run /design-ui first to generate and wire screen designs.

## Scope
Implement in `frontend/src/`:
- Page component(s): `frontend/src/pages/[FeatureName]/`
- Reusable components: `frontend/src/components/[ComponentName]/`
- Redux slice (if new state needed): `frontend/src/store/[feature]Slice.ts`
- API module (axios calls): `frontend/src/api/[feature]Api.ts`
- Route registration in `frontend/src/router/`

⚠️ The API module MUST read `.data` from every ApiResponse<T>:
```typescript
// ✅ CORRECT
const response = await axios.get<ApiResponse<User[]>>('/api/users');
return response.data.data;  // axios .data = HTTP body; ApiResponse<T> .data = payload

// ❌ WRONG — causes blank screen
return response.data;         // returns ApiResponse<T> wrapper, not T
return response.data.items;   // key doesn't exist
```

## data-testid Attribute Map
*(Required — every interactive element must have a data-testid)*
| Element | data-testid value |
|---------|------------------|
| [element description] | [kebab-case-id] |

## Frontend Unit Test File Spec
File: `frontend/src/tests/[ComponentName].test.tsx`
Committed in SAME PR as the component.
Must cover UT-FE- IDs assigned to this issue.
Mock API modules; mock return values MUST use `{ data: [...] }` envelope (never bare arrays).

## Test IDs (UI)
*(Included when ai-context/test-plan.md exists)*
| Type | IDs | Who writes them |
|------|-----|-----------------|
| Unit (UT-FE-) | [UI-specific UT-FE- IDs] | Ralph-impl — same PR as component |

## Dependencies
Blocked by: F-XX-API-001 (API layer must be complete first)

## Definition of Done
- [ ] ⚠️ At least one `.tsx` React file created in `frontend/src/` — NO EXCEPTIONS
- [ ] All SCR-NNN screens implemented matching the approved mockup
- [ ] API module uses `response.data.data` pattern (not `response.data` or `response.data.items`)
- [ ] All `data-testid` attributes from the map are present in component source
- [ ] Frontend unit test file (`frontend/src/tests/[ComponentName].test.tsx`) committed in this PR
- [ ] All UT-FE- IDs written and passing (`npm run test -- src/tests/[ComponentName].test.tsx`)
- [ ] `tsc --noEmit` passes with zero errors — no `any` types
- [ ] PR merged and issue closed

⛔ IMPLEMENTATION WITHOUT A REACT FILE IN `frontend/src/` = DoD FAILURE.
   Label: `ui-impl-missing`. Do not close the issue. Do not mark COMPLETE.
```

## Step 3 — Assign Labels and Wave

Every issue gets these labels derived from the feature file:
- `wave:[1|2|3]` — from Execution Wave
- `feature:[F-XX]` — feature ID
- `layer:[DB|API|UI|INT|TEST|E2E]` — implementation layer (mandatory — used by /ralph to route to agents)
- `priority:[must|should|could]` — from highest-priority FR in this feature

---

## Step 4 — Build Dependency Graph

Use the "Depends on / Blocks" fields in each feature file to build the execution order:

- Features in Wave 1 with no dependencies: `execution_order: 1`
- Features that depend on Wave 1 features: `execution_order: 2`
- And so on

Issues within the same feature that have no inter-dependency: mark `"type": "parallel"`.

## ⛔ HIL — Issue Review

After generating `ai-context/issues.json`, present a layer-split summary and verify UI issues are present:

```
⛔ ISSUE REVIEW
[N] epics | [N] issues across [N] waves
has_frontend: [true/false] | frontend_stack: [value]

Layer breakdown:
  DB:   [N] issues
  API:  [N] issues
  UI:   [N] issues  ← must be > 0 when has_frontend is true
  INT:  [N] issues
  TEST: [N] issues
  E2E:  [N] issues

Wave 1 ([N] issues — start immediately):
  F01-DB-001  [F-01] Feature Name — DB Layer
  F01-API-001 [F-01] Feature Name — API Layer
  F01-UI-001  [F-01] Feature Name — UI Layer
  ...

Wave 2 ([N] issues — after Wave 1):
  F02-DB-001  ...

Wave 3 ([N] issues):
  ...

Screen Reference sources:
  From feature files (## Screen References): [N] features
  From fallback ai-context/ui-design.md:     [N] features
  Missing (no source found):                 [N] features ← must be 0

⚠️ VALIDATION:
  - has_frontend is true but UI issues = 0 → HALT. Run /design-ui first, then re-run /feature-to-issues.
  - No layer field on any issue → HALT. Regenerate with layer-split format.
  - Any UI issue missing screen_refs (source = missing) → HALT. Re-run /design-ui to wire feature files first.

Type YES to confirm and proceed to /push-to-pms.
Type REVISE [issue-id] [change] to update an issue.
```
