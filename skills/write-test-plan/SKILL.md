# /write-test-plan — Test Plan Generator

**Inputs:**
- `docs/prd.md` ✓ (FR-n, AC-n, PT-n IDs)
- `docs/features/F-XX-*.md` ✓ (User Stories, Acceptance Criteria per feature)
- `ai-context/ui-design.md` ✓ if present (SCR-NNN screen inventory, states, Primary Actions)
- `ai-context/coding-standards.md` ✓ (test framework from /constitution)

**Outputs:**
- `docs/test-plan.md` — full test plan (human-readable)
- `ai-context/test-plan.md` — compact version consumed by /feature-to-issues and /ralph

Run immediately. No preamble.

---

## Core Rule: Requirements-Derived Only

Every test case must trace to at least one FR-n or AC-n from `docs/prd.md`.
A test case with no traceable requirement is scope creep — flag it instead of including it.

**Never** reference implementation files, function names, or database schemas.
Tests are written from what the system must DO, not how it does it.

---

## Step 1 — Extract Test Framework

Read `ai-context/coding-standards.md` (generated by /constitution).
Extract:
- Unit test framework (e.g. Vitest, Jest, pytest, JUnit 5, xUnit)
- Any stated coverage gate (default to 80% if not specified)

If not found, ask inline: *"What unit test framework will this project use?"*

---

## Step 2 — Unit Tests (UT-)

**Scope:** Every MUST-priority AC from `docs/prd.md` must have at least one UT-.
SHOULD-priority ACs get unit tests where the behaviour is self-contained (no external dependency).

For each AC, write:

```
UT-[N] (FR-[ref], AC-[ref], Feature: F-XX)
Scenario   : [what input or state is being tested]
Expected   : [exact expected output or behaviour]
Framework  : [from coding-standards.md]
```

**Frontend screens** (from `ai-context/ui-design.md` — skip if file absent):
For each SCR-NNN, derive these 6 minimum scenarios:

```
UT-[N] (SCR-[ref], Feature: F-XX) — Render
  Component mounts; all primary fields and actions are present.

UT-[N] (SCR-[ref], Feature: F-XX) — Loading state
  API call pending; loading indicator visible; no data rendered.

UT-[N] (SCR-[ref], Feature: F-XX) — Empty state
  API returns no data; empty-state message visible; table/list absent.

UT-[N] (SCR-[ref], Feature: F-XX) — Error state
  API call fails; error message visible; no partial data shown.

UT-[N] (SCR-[ref], Feature: F-XX) — Happy path
  User completes the Primary Action successfully; success feedback shown.

UT-[N] (SCR-[ref], Feature: F-XX) — Failure path
  Primary Action fails (API error); error feedback shown; state unchanged.
```

Number UT- sequentially across the entire plan (UT-01, UT-02, ...).

---

## Step 3 — Integration Tests (IT-)

**Scope:** Every boundary crossing between two parts of the system — frontend↔backend,
backend↔database, backend↔external service, service↔service.

Derive boundaries from:
- Feature files: "Integration Points" sections
- PRD: any FR describing data flow between layers
- UI design: screens that fetch or submit data (each is a frontend↔backend boundary)

For each boundary:

```
IT-[N] (FR-[ref], Feature: F-XX)
Boundary   : [Service A → Service B] or [Frontend → API endpoint]
Scenario   : [what flow is being validated end-to-end]
Setup      : [what test data or state must exist before the test runs]
Steps      : [numbered: 1. do X, 2. verify Y]
Expected   : [final state in both services / what the response must contain]
```

**Key assertions every IT- must make:**
- HTTP status code
- Response body contains expected fields (not just status 200)
- State change persisted (if write operation)
- Auth/permission enforced (if protected endpoint)

Number IT- sequentially (IT-01, IT-02, ...).

---

## Step 4 — Smoke Tests (SMK-)

**Scope:** The minimum set of tests that prove the system is alive and the critical path
works after any deployment. Fast to run (< 2 minutes total). No edge cases.

Derive from:
- PT- Playwright scenarios in `docs/prd.md` (if present) — map each PT- to one SMK-
- The single most important User Story per feature (Wave 1 features first)
- Login/auth flow (always included if auth exists in PRD)

For each smoke test:

```
SMK-[N] (PT-[ref] or FR-[ref], Feature: F-XX)
Name       : [human-readable scenario name]
Actor      : [user role]
Steps      :
  1. [Navigate to / open]
  2. [Perform action]
  3. [Assert visible result]
Expected   : [what must be true for this test to pass]
Criticality: BLOCKING — deployment fails if this test fails
```

Rules:
- Maximum 1 SMK- per feature (pick the most critical User Story)
- Total smoke suite must be runnable in < 2 minutes
- Every SMK- must be independently runnable (no shared state between tests)

Number SMK- sequentially (SMK-01, SMK-02, ...).

---

## Step 5 — Regression Tests (RT-)

**Scope:** The set of existing tests that must re-run and pass whenever a change is made,
to catch regressions. This is not new test writing — it is a register that maps ACs to
their covering test(s) and marks the ones that are regression-critical.

For each AC that is:
- MUST priority, OR
- Covered by a previous bug fix (flag these explicitly), OR
- On the critical user path (auth, data integrity, billing, permissions)

Write:

```
RT-[N] (AC-[ref], FR-[ref], Feature: F-XX)
Covered by  : [UT-N and/or IT-N that covers this AC]
Risk        : HIGH / MEDIUM / LOW
Trigger     : [what kind of change should force this to re-run:
               "any change to auth module" / "any PR touching F-XX" / "all PRs"]
```

The regression register tells /ralph and CI which tests to run on which PRs —
not every test needs to run on every PR.

Number RT- sequentially (RT-01, RT-02, ...).

## ⛔ HIL — Test Plan Review

```
⛔ HITL — TEST PLAN REVIEW

Counts:
  Unit tests (UT-):        [N]
  Integration tests (IT-): [N]
  Smoke tests (SMK-):      [N]  (estimated runtime: [N] min)
  Regression entries (RT-): [N]

Checklist:
  □ Every MUST-priority AC has at least one UT-
  □ Every service boundary in the features has an IT-
  □ Every feature has exactly one SMK- (the most critical story)
  □ All HIGH-risk ACs are in the regression register
  □ Smoke suite estimated runtime is under 2 minutes
  □ FR/AC Coverage Matrix has no gaps on MUST rows

Type YES to confirm and proceed to /feature-to-issues.
Type REVISE [test-id or item] [change] to update before confirming.
```
