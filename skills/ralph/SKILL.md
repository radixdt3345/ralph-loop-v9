# /ralph — Forge Multi-Agent Build Orchestrator (v6)

Run immediately when triggered. No preamble.

**Authority rule**: /ralph owns the build execution. It never re-implements
skills' logic. When /lsp is called, follow its SKILL.md exactly.
When /production-readiness is called, follow its SKILL.md exactly.

---

## Prerequisites (verify before starting)

- [ ] `ai-context/issues.json` exists and is valid
- [ ] `ai-context/project-constitution.md` exists (generated by /constitution)
- [ ] `ai-context/coding-standards.md` exists (generated by /constitution)
- [ ] `ai-context/testing.md` exists (generated by /constitution — has test framework, env config, E2E tool)
- [ ] `ai-context/ralph-agent-spec.md` exists (generated by /constitution — has branch strategy, domain map, concurrency caps)
- [ ] `ai-context/database-guidelines.md` exists (generated by /constitution)
- [ ] `ai-context/pms-map.json` exists (generated by /push-to-pms)
- [ ] `task_status.md` exists (generated by /push-to-pms)
- [ ] GitHub repo exists with issues populated (from /push-to-pms)
- [ ] `ai-context/pms-map.json` maps internal IDs to GitHub issue numbers

If any prerequisite is missing, halt and report which step to re-run.

---

## The Build Loop

```
Phase A — Orchestrator init
Phase B — Tier 1: Domain-parallel Ralph-impl waves
Phase C — Ralph-test (sequential per feature after impl)
Phase D — Ralph-e2e (sequential per feature after test)
Phase E — /production-readiness
```

## Phase A — Orchestrator Init

### A1. Load State
Read:
- `ai-context/issues.json`
- `ai-context/pms-map.json`
- `ai-context/ralph-agent-spec.md` — branch strategy, domain map, concurrency caps
- `ai-context/testing.md` — test framework, environment, E2E tool and staging URL
- `ai-context/project-constitution.md`
- `ai-context/coding-standards.md`
- `task_status.md`

### A1.5. Frontend Prerequisite Gate ⚠️

After loading state, read `has_frontend` from `ai-context/ralph-agent-spec.md`.

**If `has_frontend` is true (or the field is absent and the PRD/constitution mention a frontend stack):**

1. **Check for `ai-context/ui-design.md`:**
   - If the file does NOT exist → **HALT immediately**:
     ```
     ⛔ FRONTEND PREREQUISITE MISSING

     This project declares has_frontend: true, but ai-context/ui-design.md is absent.
     /ralph cannot build UI layers without an approved screen design.

     Required action:
       1. Run /design-ui to generate screen wireframes and SCR-NNN IDs
       2. Re-run /feature-to-issues to regenerate issues.json with UI issues referencing SCR-NNN
       3. Re-run /push-to-pms to create the UI issues in GitHub
       4. Then re-run /ralph

     Do NOT skip /design-ui. UI issues generated without SCR-NNN references
     will be implemented as API-only, leaving the frontend entirely unbuilt.
     ```
   - Do not proceed until the user has run `/design-ui` and confirms.

2. **Check that UI-layer issues exist in `ai-context/issues.json`:**
   - Count issues where `"layer": "UI"`.
   - If count = 0 → **HALT**:
     ```
     ⛔ NO UI ISSUES IN ISSUES.JSON

     has_frontend is true and ai-context/ui-design.md exists, but issues.json
     contains zero UI-layer issues.

     Required action:
       1. Run /feature-to-issues again
       2. Run /push-to-pms to create the new UI issues in GitHub
       3. Then re-run /ralph
     ```
   - Do not proceed until UI issues exist.

**If `has_frontend` is false:** skip both checks above and proceed normally.

### A2. Identify Eligible Issues
An issue is ELIGIBLE for Ralph-impl if:
1. Layer is DB, API, UI, or INT
2. All blocking dependencies are COMPLETE (closed in GitHub)
3. Current status in `task_status.md` is PENDING

An issue is ELIGIBLE for Ralph-test if:
1. Layer is TEST
2. All sibling impl issues for the same feature are COMPLETE

An issue is ELIGIBLE for Ralph-e2e if:
1. Layer is E2E
2. All sibling TEST issues for the same feature are COMPLETE

### A3. Build Execution Order
Read `execution_order` and `dependencies` from `ai-context/issues.json`.
Print initial status:
```
🔨 FORGE BUILD START (v6)
Issues total:  [N]
Ralph-impl:    [N] (DB/API/UI/INT)
Ralph-test:    [N] (TEST)
Ralph-e2e:     [N] (E2E)
Domains:       [list]
API contracts: [N endpoints in registry]
```

## Phase B — Ralph-impl Waves

### Tier 1 — Domain Parallelism
For each wave:
1. Identify all domains with eligible impl issues
2. Spawn one domain-worker per domain (up to max from ralph-agent-spec, default 4)
3. Each domain-worker runs in its own git worktree at `../[repo-slug]-wt-[domain-lowercase]`

### Tier 2 — Issue Parallelism Within a Domain
Each domain-worker processes layers in order: DB → API → UI → INT
Within each layer-stage, spawn one issue-worker per eligible issue (max 3 per stage).

---

### Ralph-impl Agent Execution (per issue)

**1. Read inputs:**
- Assigned GitHub issue (fetch from GitHub API using issue number from pms-map.json)
- `docs/features/F-XX-[slug].md`
- `ai-context/project-constitution.md`
- `ai-context/coding-standards.md`
- `ai-context/testing.md`
- `ai-context/database-guidelines.md` (DB issues)
- `ai-context/repo-structure.md`

**2. Create feature branch:**
```bash
git fetch origin
git checkout -b feat/[GITHUB-ISSUE-ID]-[slug] origin/main
```

**3. Implement:**

**For DB tasks:**
- Write schema migrations and seed files only
- Follow `ai-context/database-guidelines.md` exactly
- Write owned UT- tests

**For API tasks — ADDITIONAL REQUIREMENTS (v6):**

3a. **Import types from shared contract file — never redefine locally:**
```typescript
// ✅ CORRECT
import type { UserDto, CreateUserDto } from '../types';

// ❌ WRONG — local type redefinition causes mismatches
interface MyResponse { data: User[] }
```

3b. **Wrap every response in ApiResponse<T>:**
```typescript
// ✅ CORRECT — controller returns ApiResponse<T>
return res.json({ data: users } satisfies ApiResponse<User[]>);

// ❌ WRONG — bare return causes blank screen on frontend
return res.json(users);
return res.json({ items: users });
return res.json({ result: users });
```

3c. **Update the contract registry after implementation.**

3d. **Write UT- tests that assert the response envelope:**
```typescript
it('returns ApiResponse<T> envelope', async () => {
  const response = await request(app).get('/api/[resource]');
  expect(response.status).toBe(200);
  expect(response.body).toHaveProperty('data');
  expect(Array.isArray(response.body.data)).toBe(true);
});
```

**For UI (frontend) tasks — ADDITIONAL REQUIREMENTS (v6):**

3e. **Verify API module accesses `.data` from the response:**
```typescript
// ✅ CORRECT
export const fetchUsers = async (): Promise<User[]> => {
  const response = await axios.get<ApiResponse<User[]>>('/api/users');
  return response.data.data;
};

// ❌ WRONG
export const fetchUsers = async () => {
  const response = await axios.get('/api/users');
  return response.data;          // ApiResponse<T>, not T — blank screen
  return response.data.items;    // Key doesn't exist — undefined
};
```

3f. **Add `data-testid` to every interactive element** per the "data-testid Attribute Map" in the task file. Missing testids = DoD failure.

3g. **Create the frontend unit test file** specified in the task's "Frontend Unit Test File Spec":
- File: `frontend/src/tests/[ComponentName].test.tsx`
- Committed in the SAME PR as the component — never deferred
- Cover ALL UT-FE- IDs listed in the task file
- Minimum 6 test scenarios (render, loading, empty, error, happy path, failure path)

**Test file structure — enforced (v6):**
```tsx
// 1. Mock ALL API modules used by the component
vi.mock('../api/[module]Api', () => ({ fn: vi.fn() }));

// 2. ⚠️ ALL mocked return values MUST use ApiResponse<T> envelope
const defaultData = { data: [{ id: '1', name: 'Alice' }] };

// 3. Mock @mui/x-data-grid DataGrid if the component uses it
vi.mock('@mui/x-data-grid', () => ({
  DataGrid: ({ rows, loading, columns }) => {
    if (loading) return <div role="progressbar" />;
    if (!rows.length) return <div data-testid="empty-grid">No rows</div>;
    return (
      <div data-testid="grid">
        {rows.map(row => {
          const actionsCol = columns.find(c => c.field === 'actions');
          return (
            <div key={row.id} data-testid={`grid-row-${row.id}`}>
              {actionsCol?.renderCell?.({ row, value: undefined })}
            </div>
          );
        })}
      </div>
    );
  }
}));

// 4. Mock useNavigate if component navigates post-submit
vi.mock('react-router-dom', async () => {
  const actual = await vi.importActual('react-router-dom');
  return { ...actual, useNavigate: () => vi.fn() };
});

// 5. Use configureStore with preloadedState — never real store
function makeStore() {
  return configureStore({
    reducer: { auth: authReducer, notifications: notificationsReducer },
    preloadedState: { auth: { user: {...}, isAuthenticated: true } },
    middleware: gm => gm({ thunk: true }),
  });
}

// 6. beforeEach: clearAllMocks + reset API mocks to happy-path defaults
beforeEach(() => {
  vi.clearAllMocks();
  vi.mocked(api.fetchData).mockResolvedValue({ data: defaultItems });
});

// 7. Use getByTestId() for interactive/observable elements
//    NEVER use querySelector or class-based selectors
```

**Validation before PR:** run `npm run test -- src/tests/[ComponentName].test.tsx`
All UT-FE- IDs must pass before creating the PR.

**For INT tasks:**
- Wire DB + API + UI into working integrated whole
- Smoke test the integration end-to-end locally before PR
- Verify API responses reach the frontend correctly (no key mismatch)

---

**4. ⛔ TypeScript Compile Gate (HARD GATE — runs before /lsp and before PR creation):**

```bash
tsc --noEmit
```

Run on ALL changed files.

**This gate is non-negotiable. No PR is created while compile errors exist — not even one error.**

- Fix every error. Do NOT use `any`, `@ts-ignore`, or `@ts-expect-error` to suppress.
- After each fix attempt, re-run `tsc --noEmit` to confirm.
- If zero errors: log `✅ tsc --noEmit: PASSED` and proceed to /lsp.
- If errors persist after **3 fix attempts**:
  1. Label the issue `ts-compile-blocked`
  2. Mark `BLOCKED_ERROR` in `task_status.md`
  3. **Do NOT create the PR**
  4. **Do NOT pick up the next issue**
  5. Notify orchestrator immediately — see **Compile Blocker Protocol** below

---

**5. Validate with /lsp (blocking gate):**
Run `/lsp` per its SKILL.md on the changed files.
- LSP Errors → fix before PR. No exceptions.
- LSP Warnings → document in PR, proceed.

**6. Create PR:**
```
Title: [GITHUB-ISSUE-ID] [issue title]
Body:
  Closes #[github-issue-number]

  ## Changes
  [brief description]

  ## FR Coverage
  [FR- IDs implemented]

  ## Test Coverage
  Backend: [UT- IDs]
  Frontend: [UT-FE- IDs with pass/fail]

  ## data-testid Attribute Map
  [confirm all testids from task file are implemented]

  ## API Contract Validation (v6)
  | Endpoint | Backend returns | Frontend reads | TypeScript compile |
  |----------|-----------------|----------------|-------------------|
  | [path]   | { data: T }     | response.data  | ✓ zero errors     |

  Mock shapes in UT-FE- tests: { data: T } ✓

  ## Compile Gate
  tsc --noEmit: ✅ PASSED (zero errors)

  ## LSP Status
  [clean / warnings listed]
```

**7. Wait for CI + merge**

**8. Update task_status.md** — mark COMPLETE

**9. Close issue in GitHub** (auto-closes via "Closes #N")

**10. Notify orchestrator**

**11. Clean up worktree**

---

### Compile Blocker Protocol (Orchestrator)

When any Ralph-impl agent reports `ts-compile-blocked`:

1. **Stop the domain immediately** — do not start any further issues in that domain's current or future layer-stages.
2. **Do not start dependent issues** in any domain that depend on the blocked issue.
3. **Print this blocking summary to the user:**

```
⛔ BUILD PAUSED — COMPILE BLOCKER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Blocked issue : [ISSUE-ID] [Issue Title]
Branch        : feat/[GITHUB-ISSUE-ID]-[slug]
Label         : ts-compile-blocked
Attempts      : 3 (max reached)

Compile errors must be fixed before this PR can be created.
Ralph will NOT automatically retry. No further issues will
be started in this domain until this blocker is resolved.

Dependent issues that cannot start until resolved:
  [ISSUE-ID] — [title] (blocked by compile failure above)
  [ISSUE-ID] — [title]
  ...

Action required:
  1. Check out branch: feat/[GITHUB-ISSUE-ID]-[slug]
  2. Fix the TypeScript compile errors (run: tsc --noEmit)
  3. Push the fix to the branch
  4. Re-run /ralph to resume from this issue
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

4. **Other independent domains continue** — a compile blocker in the Auth domain does not stop the Billing domain (unless Billing depends on the blocked issue).
5. **Wait for human input.** Do not auto-retry, do not skip ahead, do not start the next issue.

---

### Failure Handling (Ralph-impl)

- **Max turns exceeded (60)**: comment on issue "Implementation incomplete after 60 turns. Needs human review." Label `needs-human`. Mark BLOCKED_ERROR.
- **LSP errors after 3 fix attempts**: label `lsp-blocked`, halt, notify orchestrator.
- **TypeScript compile errors after 3 fix attempts**: label `ts-compile-blocked`, halt, **do not create PR**, trigger Compile Blocker Protocol above.
- **Frontend tests failing after 3 fix attempts**: label `fe-test-blocked`, halt.
- **Merge conflict**: rebase off main, retry twice. If persists: label `merge-conflict`, halt.
- **CI failure**: fix and push. If not fixable in 2 attempts: label `ci-blocked`, halt.

## Phase C — Ralph-test

Triggers when ALL Ralph-impl issues for a feature are COMPLETE.
Ralph-test writes IT- integration tests per TEST issue.

### Ralph-test Agent Execution (per TEST issue)

**1. Read inputs:**
- Assigned GitHub TEST issue
- `ai-context/testing.md`
- `docs/test-plan.md` — IT- test IDs for this feature
- `docs/features/F-XX-[slug].md`

**2. Create test branch:**
```bash
git checkout -b test/[GITHUB-ISSUE-ID]-[slug] origin/main
```

**3. Write integration tests:**
- Cover ALL IT- IDs from `docs/test-plan.md` for this feature
- Validate against running test environment
- Follow `ai-context/testing.md` conventions
- DO NOT modify implementation or frontend test files
- Every HTTP endpoint test MUST assert `response.body.data` exists:
  ```typescript
  expect(response.body).toHaveProperty('data');
  // Never: expect(response.body.items) or expect(response.body.result)
  ```

**4. Run tests** — all IT- IDs must pass before PR.

**5. Create PR and merge** — closes TEST issue on merge.

**6. Failure handling:**
- Test environment unreachable: label `env-issue`, halt
- Tests failing due to API key mismatch: open bug `[BUG][HIGH] API contract violation`, label `api-contract-bug`, halt
- Tests failing after 3 fix attempts: open bug, label `needs-human`, halt

---

## Phase D — Ralph-e2e

Triggers when ALL TEST issues for a feature are COMPLETE.

### Ralph-e2e Agent Execution (per E2E issue)

**1. Read inputs:**
- Assigned GitHub E2E issue
- `ai-context/testing.md` — Playwright config, staging URL
- `docs/test-plan.md` — E2E- IDs for this feature

**2. Create e2e branch:**
```bash
git checkout -b e2e/[GITHUB-ISSUE-ID]-[slug] origin/main
```

**3. Write Playwright tests:**
- Cover ALL E2E- IDs for this feature
- Use `page.getByTestId()` for ALL interactive element selectors
- Run against staging environment
- DO NOT modify implementation or unit/integration test files

**4. Run tests** — all E2E- IDs must pass before PR.

**5. Create PR and merge** — closes E2E issue on merge.

**6. Failure handling:**
- New regression: open bug issue, block E2E issue from closing
- Staging unreachable: label `env-issue`, halt

## Orchestrator Polling

On each agent signal:
1. Refresh `task_status.md` from GitHub
2. Identify newly eligible issues
3. Spawn new agents (only for issues whose dependencies are fully COMPLETE — a BLOCKED_ERROR dependency blocks its children)
4. Print: `[timestamp] Wave [N] complete | COMPLETE: [X] | IN_PROGRESS: [Y] | PENDING: [Z] | BLOCKED: [B]`

GitHub issue state = source of truth. `task_status.md` is local mirror.
